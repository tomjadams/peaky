## MODIFIED Requirements

### Requirement: Outbox-Based Background Synchronization

The application SHALL synchronize local mutations through an outbox and cursor-based push/pull protocol, using field-level HLC timestamps for conflict resolution and `LocalMutation.replay()` for applying pulled events to local state.

#### Scenario: Local edits enqueue background sync work with HLC

- **WHEN** a local-first edit is committed to the client-local database
- **THEN** the system records a pending outbox item with per-field HLC timestamps
- **AND** the outbox `fields` column contains a JSON array of `{name, value, hlc}` objects
- **AND** the HLC is generated by the client-side HLC clock as `{wallclock_ms}:{counter_padded_4}:{actorId}`, where wallclock_ms is milliseconds since epoch and counter is zero-padded to 4 digits for lexicographic string comparison

#### Scenario: Client pushes field-level events

- **WHEN** the client pushes pending outbox items to the server
- **THEN** each event includes an `operation` of `upsert` or `delete` (not `create`/`update`)
- **AND** each event includes a `fields` array with per-field HLC stamps
- **AND** all fields are sent on every push (not just changed ones)

#### Scenario: Client pulls and replays remote changes

- **WHEN** the client pulls remote changes from the server
- **THEN** it applies each event to local SQLite via `LocalMutation.replay()`
- **AND** the replay writes to the domain state table and inserts an audit event
- **AND** the replay does NOT write to the outbox (preventing re-push loops)

#### Scenario: Replayed events are marked synced

- **WHEN** `LocalMutation.replay()` inserts an audit event for a pulled change
- **THEN** the event has `status = 'synced'` and `source = 'peaky.sync'`
- **AND** the push pipeline (which filters `WHERE status = 'pending'`) never re-queues it

#### Scenario: Inbound event handlers dispatch by entity type

- **WHEN** a pulled event arrives with a given `entityType`
- **THEN** the registered inbound event handler for that entity type applies the event
- **AND** the handler uses Drizzle upsert to write the fields to the correct local table
- **AND** new entity types can be added by registering a new handler (Strategy pattern)

#### Scenario: Inbound event handlers honor delete operations

- **WHEN** a pulled event arrives with `operation: "delete"` for an entity type whose rows can be deleted
- **THEN** the registered inbound event handler deletes the entity from the local database
- **AND** the handler does NOT attempt to upsert fields (there are none on a delete)
- **AND** the delete is recorded as a replayed event with `status = 'synced'` and `source = 'peaky.sync'`
- **AND** `FieldVersionHandler` does not honor delete because field versions are append-only audit records
