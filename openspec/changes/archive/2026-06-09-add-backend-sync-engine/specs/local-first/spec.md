## MODIFIED Requirements

### Requirement: Outbox-Based Background Synchronization

The application SHALL synchronize local mutations through an outbox and cursor-based push/pull protocol, using field-level HLC timestamps for conflict resolution and `LocalMutation.replay()` for applying pulled events to local state.

#### Scenario: Local edits enqueue background sync work with HLC

- **WHEN** a local-first edit is committed to the client-local database
- **THEN** the system records a pending outbox item with per-field HLC timestamps
- **AND** the outbox `fields` column contains a JSON array of `{name, value, hlc}` objects
- **AND** the HLC is generated by the client-side HLC clock as `wallclock:counter:actorId`

#### Scenario: Client pushes field-level events

- **WHEN** the client pushes pending outbox items to the server
- **THEN** each event includes an `operation` of `upsert` or `delete` (not `create`/`update`)
- **AND** each event includes a `fields` array with per-field HLC stamps
- **AND** all fields are sent on every push (not just changed ones)

#### Scenario: Client pulls and replays remote changes

- **WHEN** the client pulls remote changes from the server
- **THEN** it applies each event to local SQLite via `LocalMutation.replay()`
- **AND** the replay writes to the domain state table and inserts an audit event
- **AND** the replay does NOT write to the outbox (preventing re-push loops)

#### Scenario: Replayed events are marked synced

- **WHEN** `LocalMutation.replay()` inserts an audit event for a pulled change
- **THEN** the event has `status = 'synced'` and `source = 'peaky.sync'`
- **AND** the push pipeline (which filters `WHERE status = 'pending'`) never re-queues it

#### Scenario: Inbound event handlers dispatch by entity type

- **WHEN** a pulled event arrives with a given `entityType`
- **THEN** the registered inbound event handler for that entity type applies the event
- **AND** the handler uses Drizzle upsert to write the fields to the correct local table
- **AND** new entity types can be added by registering a new handler (Strategy pattern)

## ADDED Requirements

### Requirement: Client-Side HLC Clock

The application SHALL maintain a client-side Hybrid Logical Clock for stamping outbox fields with causally-ordered timestamps.

#### Scenario: HLC is monotonically increasing

- **WHEN** the HLC clock generates a new timestamp
- **THEN** the wallclock component is `max(Date.now(), lastWallclock)`
- **AND** if the wallclock equals the previous wallclock, the counter increments
- **AND** the resulting HLC is lexicographically greater than any previously generated HLC

#### Scenario: HLC format is sortable

- **WHEN** the HLC clock generates a timestamp
- **THEN** the format is `{wallclock_ms}:{counter_padded_4}:{actorId}`
- **AND** two HLCs can be compared as strings for correct causal ordering

### Requirement: Data Reaches Client Through Sync Only

The application SHALL use the sync protocol as the only channel for server data to reach the client. Pages read from local SQLite and do not make per-page REST calls for domain data.

#### Scenario: Returning user renders from local SQLite

- **WHEN** a returning user loads any domain page (teams, products, reviews)
- **THEN** the page renders from local SQLite data immediately
- **AND** the sync pull (background, non-blocking) brings in any deltas

#### Scenario: First-visit user sees empty state then populates

- **WHEN** a first-time user loads the app
- **THEN** bootstrap returns actor + entitlements + cursors (lightweight, no domain data)
- **AND** the initial sync pull streams domain data into local SQLite in the background
- **AND** the UI reactively updates as data arrives

#### Scenario: Bootstrap does not block app startup

- **WHEN** the app starts
- **THEN** SQLite WASM loads and migrations apply first (fast)
- **THEN** bootstrap completes (lightweight)
- **THEN** the app renders from local SQLite
- **AND** the initial sync pull runs in the background without blocking render
