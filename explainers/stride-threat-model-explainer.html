03 · Active threats

29 threats still open

Grouped by risk. Every row names what closes it — a phase, a mitigation, or an accepted trade-off. Four of the seven HIGH threats share one root cause: Phase 1 trusts request headers instead of a verified token, and an unrecognized actor doesn't even get rejected — it becomes a wildcard-entitled dev actor. The other three came out of the audit: an HLC nobody validates, 23 write routes nobody retired, and a directory mirror that never had the admin gate this page used to claim for it.

Deployment contract, not code: the reverse proxy / Lambda Web Adapter must strip x-actor-roles — and re-inject x-actor-id from the session — before a request reaches the Go services. Nothing in the codebase enforces this today; if that contract slips, an unverified or forged actor id isn't rejected, it becomes a fully entitled actor_dev. Verify it in the AWS WAF / ALB configuration before production traffic.

Phase 3 fix point: verified validation replaces header trust in one Go file — services/internal/middleware/actor.go — and the landing beside it takes away the last reason to keep the roles header. Both are deleted, not bypassed, so all four header-trust HIGH rows cease to exist: the roles header owns two of them (S and E), and the fourth row above is why it survived this long. It does nothing for the other three HIGH threats — the unvalidated HLC, the Nitro write surface, and the unauthenticated directory mirror are separate work, and none of them is scheduled. Formal verification doesn't reach this gap either — every FizzBee spec in formal_verification/ assumes an honest, already-identified client; spoofing is out of scope by design.

04 · Roadmap

Why these wait, not whether

Every gap above is tracked, not forgotten — but "tracked" no longer means "scheduled". Grouped by the phase that closes it, with an honest Unscheduled tier for the three the audit surfaced: they wait on a decision, not a dependency. The right column repeats only the risk level, not the full threat — see Active Threats for that. Eight FizzBee specs in formal_verification/ back several mitigations with proofs (see Active Threats for the CI-coverage caveat), and a drift guard — tests/guards/threat-model-drift.test.ts — pins this page's paths, caps, and entity types to the code. It does not pin the prose, which is how the mitigation ledger drifted in the first place.

The facts announce themselves: every mechanically checkable claim above is tied to the code that owns it, and the tie runs at commit time — not just in CI.

→ commit blocked; the failure names the marker — the fix is a one-line edit next to it.

The same guard checks entity types against the Go registry and every cited file path with existsSync — a deletion trips it too, via --no-renames --diff-filter=D in .husky/pre-commit. The threat model can no longer rot silently: these are the facts a machine can check, and they fail the commit on the author's own machine, before a reviewer ever sees it.
