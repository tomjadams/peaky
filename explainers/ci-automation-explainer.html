as events.

Features subscribe to GitLab events via RUNS_ON and return the writes they want. The framework reads, runs them in parallel, and applies every action in one auditable write seam. Adopt it as a CI job today; grow into a hosted webhook server later by swapping one adapter — the core never changes.

TL;DR

Event-driven plugins. Each feature subscribes via RUNS_ON. Adding one is a config model + RUNS_ON + a pure run() — nothing else to wire.

Pure features return actions. They read state and return AddLabel(…) / SetTitle(…); the framework applies them in one serial write seam after the pool joins. Purity is what makes parallel safe.

Grows without a rewrite. The typed is GitLab-faithful. Env today, webhook later is an adapter swap — Event, Feature, RUNS_ON, actions, and client are unchanged.

Dry run is first-class. CI_AUTOMATION_DRY_RUN=1 previews exactly what would happen — reads run, nothing mutates, exit 0.

01 · Before

The visibility problem

GitLab CI gives you a job, not a step. When governance checks live inside one job, the pipeline can't tell you which one broke — and running them as separate jobs pays a cold-start tax for <1s of work each.

02 · The architecture

One entry point, pure features, one write seam

A single entry point builds a typed , discovers every feature, and runs the ones that subscribe to it through a . Each feature gets a and stays pure — it reads state and returns ; the framework applies every one of them in a single serial phase after the pool joins.

Concurrency is in service of the model, not the headline — it's safe only because a feature never mutates mid-run, so two running at once can't race on MR state.

First-class · Dry run

One env var, a full preview

Set CI_AUTOMATION_DRY_RUN=1 and the toolkit runs for real, then stops before anything is written.

Reads still execute, so the verdict in the log is the true verdict — and the run doubles as a token and permissions check. Nothing mutates.

It's effectively free: because features are pure and every write funnels through one seam, dry run just gates that seam. Features never learn about it.

06 · Project layout

One file per concern

The client adapter is the single port to GitLab — anything that talks to GitLab goes through GitLabClient, so features stay isolated and testable.

Tests live in tests/unit/ with doubles for the GitLab client — no I/O, fast, deterministic. The FeatureTestHarness provides a fluent builder so feature authors write 4-line tests, not 12 lines of mock setup.
