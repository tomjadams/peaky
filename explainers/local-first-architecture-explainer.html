Save here, sync in the background. The browser is the primary source of truth for a write — the server catches up, not the user.

TL;DR

The one rule: write to local SQLite first, push to the server in the background. The user never waits on the network.

Conflicts resolve per field with a Hybrid Logical Clock. Server-sent events wake connected peers instantly — no polling, no domain data on the wire.

What stays the same: PostgreSQL is still the durable, authoritative store. It just isn't in the hot path of a save anymore.

01 · The problem

Every save waits on the network

Client → server → Postgres → client. Simple to reason about. The wait becomes the whole experience once a team spans continents.

Most apps default to one model: click Save, wait for the server's response, then update the UI. In a single office the round trip is 2–5 ms — no one notices.

Across continents it is the dominant experience. Every save pays the network cost in full, twice over: once out, once back.

02 · The fixes that fail

Replication and pub-sub trade one problem for another

Neither approach changes where a write lands first. The server stays in the critical path, and each new layer adds its own failure mode.

Neither of these moves where writes land first. The server is still in the critical path — every new layer just adds its own failure mode.

03 · Local-first: flip the model

Write local. Sync in the background.

Make the browser the immediate source of truth. Let the server be the background authority — additive to the interaction loop, not foundational to it.

Instead of: click → wait for the server → update the UI. Local-first: click → write to local SQLite (≈1 ms) → update the UI → sync to the server in the background. If the network is slow or fully down, the change queues in an outbox and flushes when connectivity returns.

04 · The shape

Two processes, one shared schema

The browser owns the write path. The server owns durability and fan-out. shared/db/schema/* is the one authority both read from.

05 · One instant experience, three continents

The write is local. The sync is a pipeline.

Amsterdam at 9 AM, Singapore at 11 PM — write latency is the same everywhere, because the network is never in the path of the write itself.

Every Peaky user writes against a local SQLite database that lives in and persists across page loads. When two people edit the same field at once, both changes reach the server; the loser is never silently dropped — it loses one field's conflict, not the whole write.

06 · Resilience

The client doesn't depend on the server being up

Traditional apps fail two ways when the network degrades: a spinner until it returns, or a silently dropped write. Local-first avoids both — the queues and flushes whenever connectivity allows, even hours later.

07 · Conflicts & HLC

Two people, one field, at the same time

Local-first removes the server from the write path — so two people can edit the same field while offline or on high latency. Something has to decide, deterministically, which write wins.

A traditional server serializes every write; the second one silently overwrites the first, and the user never finds out. Local-first can't rely on that — writes arrive out of order, sometimes hours apart.

Wall-clock "last write wins" fails too: client clocks drift. A laptop resuming from sleep can read 90 seconds behind — every write from it would lose, always.

A combines the wall clock, a logical counter, and the actor's id into one string. Comparing two HLCs lexicographically gives a total order that survives clock drift and stays correct even within the same millisecond.

HLC wire format

conflict.go
"1716220800000:0001:actor_alice"
// wallclock (unix ms) : counter (zero-padded, 4 digits) : actorId (deterministic tiebreak)
08 · Real-time updates

Real-time, without domain data on the wire

Without , a browser polls every 30 seconds. With it, PostgreSQL's own notify wakes every entitled peer the moment a push lands.

No field values. No user data. No secrets. peaky-sse never holds domain data — it cannot leak what it does not have.
